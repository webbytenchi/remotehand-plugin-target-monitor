# Target Monitor v1.0.0 Design

Target Monitor expands the proven Host Monitor foundation into generic target, service, and endpoint monitoring for RemoteHand.

## Core model

One target can monitor:

- ICMP / Ping
- Multiple TCP ports
- Multiple HTTP / HTTPS requests

One target produces exactly one top-bar contribution.

Top-bar presentation and alert evaluation are independent.

## Ping

The existing ICMP / Ping implementation and alert behavior are considered stable and should remain unchanged.

Existing latency sampling, history, state classification, and alert semantics should be preserved.

## TCP Port Checks

Each target may have multiple TCP port checks.

Common service presets should include:

- HTTP — 80
- HTTPS — 443
- SSH — 22
- RDP — 3389
- SMB — 445
- DNS — 53
- SMTP — 25
- IMAP — 143
- POP3 — 110
- MySQL — 3306
- PostgreSQL — 5432

A Custom option allows a user-defined name and port.

## HTTP / HTTPS Checks

HTTP / HTTPS monitoring is content-agnostic.

Each request captures:

- HTTP status
- response time
- content type
- raw response body

Adding a request should initially require only:

- Name
- URL

Rich configuration happens afterward in a separate modal.

### JSON

For JSON responses:

- discover fields
- prettify field names and values
- allow numeric fields as graph sources
- allow text and numeric fields to participate in alerts

### Plain Text

For plain-text responses:

- display the response
- support whole-response value display
- support text-change alerting

### Regex

Non-JSON replies may use regex extraction.

Named capture groups become monitored fields.

Example regex:

temperature=(?<temp>[0-9.]+)

Numeric captures may be treated as numeric values; other captures remain text.

The UI should provide Test / Preview before saving a regex.

HTML should be handled as response content or readable text, not rendered as an arbitrary web page inside Target Monitor.

## Add Target

Keep the Add Target flow simple.

Basic target properties:

- Name
- Host / IP
- Enabled

Monitoring sections:

- Ping
- TCP ports
- HTTP / HTTPS requests

TCP uses Add Port.

HTTP / HTTPS uses Add Request and initially asks only for name + URL.

Detailed HTTP field configuration happens after the request is added.

## Targets View

The current ping-centric layout should evolve because one target may contain Ping, TCP, and HTTP / HTTPS checks.

Each row should summarize:

- target identity
- overall state
- Ping status
- TCP summary
- HTTP / HTTPS summary
- actions

The current lower Ping-only dashboard containing Current latency, Packet loss, Samples, and Recent latency should be removed from the main Targets view for now.

The underlying Ping history functionality should remain available for relocation into a richer detail/report view later.

## Top Bar

Exactly one top-bar item exists per target.

The user chooses the source for:

- Title
- Value
- Graph

Any slot may be None.

Example:

Title: Bitaxe
Value: hashRate_10m
Graph: temp

Numeric monitored values may be used for graphing.

Fields not shown in the top bar continue to be monitored and may still trigger alerts.

## Alerts

Alert sounds move into a dedicated Alerts tab.

Existing Ping alert behavior remains unchanged.

Target Monitor adds reusable named alert definitions.

Examples:

- HighTemp
- CriticalTemp
- LowHashrate
- PoolChanged
- Alert1

A generic alert contains:

- Name
- Operator
- Comparison value when required
- Sound

Numeric operators:

- >=
- <=
- =

Text/value rules:

- equals
- changed

A monitored field may have zero, one, or multiple assigned alerts.

## Alert Evaluation

Alerts run independently from top-bar presentation.

Sounds are transition-based.

When a rule becomes active:

- mark it active
- play its configured sound once
- mark the target as having an unacknowledged alert

Do not replay the sound every polling cycle while the condition remains active.

## Alert Badge and Acknowledgment

If any field on a target has an unacknowledged alert, the target's single top-bar item shows an alert badge.

The top-bar's configured Title, Value, and Graph remain unchanged.

Clicking the target top-bar item:

- opens or focuses the target report
- acknowledges currently unread alerts
- clears the top-bar alert badge

Acknowledgment does not resolve the alert.

### Active + Unacknowledged

- sound plays on transition
- top-bar badge visible
- report shows active alert

### Active + Acknowledged

- top-bar badge cleared
- no repeated sound
- report still shows active alert

### Resolved

- condition is no longer true
- alert is no longer active

If a resolved condition triggers again later, it becomes a new alert event.

## Example: AxeOS / Bitaxe

AxeOS is a useful example of the generic HTTP / JSON model, not a hard-coded device type.

A response from /api/system/info may expose values such as:

- hashRate_10m
- temp
- vrTemp
- power
- fanrpm
- wifiRSSI
- stratumURL
- miningPaused
- overheat_mode

Example top-bar configuration:

Title: Bitaxe
Value: hashRate_10m
Graph: temp

Other fields may still participate in background alerts.

## Product Boundary

Target Monitor should remain generic and user-controlled.

Do not hard-code device-specific dashboards unless real usage later justifies them.

The v1.0.0 goal is:

- proven Ping monitoring
- TCP reachability
- HTTP / HTTPS monitoring
- JSON, text, and regex extraction
- one top-bar item per target
- reusable alerts
- clear acknowledgment and resolution behavior

Avoid turning v1.0.0 into a full enterprise monitoring platform.
