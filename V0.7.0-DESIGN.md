# Target Monitor v0.7.0 Design

Target Monitor v0.7.0 expands the proven Host Monitor v0.6.1 foundation into generic target, service, endpoint, and alert monitoring for RemoteHand.

This document describes the delivered v0.7.0 product model.

## Core model

One target can monitor:

- ICMP / Ping
- multiple TCP ports
- multiple HTTP / HTTPS requests

One enabled target produces at most one Target Monitor top-bar contribution.

Monitoring, presentation, alert evaluation, and alert delivery are separate concerns.

## Ping

The inherited ICMP / Ping implementation remains the stable monitoring foundation.

Target Monitor preserves:

- real ICMP latency sampling
- Normal / High Latency / Offline state classification
- two-sample state confirmation
- retained latency history
- transition-based Ping alerts
- custom alert sounds with fallback beep
- optional reminders
- per-target tray graph support

Ping graph coloring follows real Ping state instead of generic numeric thresholds.

## TCP port checks

Each target may have multiple TCP port checks.

Common service presets include:

- HTTP — 80
- HTTPS — 443
- SSH — 22
- RDP — 3389
- SMB — 445
- DNS — 53
- SMTP — 25
- IMAP — 143
- POP3 — 110
- MySQL — 3306
- PostgreSQL — 5432

A Custom option allows a user-defined service name and port.

TCP checks expose reachability and connection-time sources.

## HTTP / HTTPS checks

HTTP / HTTPS monitoring is content-agnostic.

Each request may expose:

- HTTP status
- response time
- content type
- raw / whole response
- discovered or extracted fields

### JSON

For JSON responses:

- fields are discovered
- field names are presented with friendly labels
- numeric fields may be graphed
- text and numeric fields may participate in alerts
- fields may define display Prefix/Suffix formatting

### Plain text

For plain-text responses:

- the response may be displayed as a monitored value
- whole-response change detection is supported
- text alert rules may be assigned

### Regex

Non-JSON replies may use regex extraction.

Named capture groups become monitored fields.

Example:

    temperature=(?<temp>[0-9.]+)

Numeric captures may be treated as numeric values; other captures remain text.

The UI provides Test / Preview before saving extraction settings.

HTML is handled as response content or readable text rather than rendered as an arbitrary web page.

## Targets view

The Targets view summarizes:

- target identity
- overall state
- Ping status
- TCP status
- HTTP / HTTPS status
- active/unread alert status
- report/edit/remove actions

Target reports hold the richer detail that would otherwise overload the main target list.

## Top bar

Exactly one Target Monitor top-bar item may exist per enabled target.

The user independently chooses the source for:

- Title
- Value
- Graph

Any slot may be None.

Example:

    Title: Bitaxe
    Value: System Info · hashRate_10m
    Graph: System Info · temp

Fields not shown in the top bar remain monitored and may still trigger alerts.

### Value colors

The top-bar Value uses two user-configurable colors:

- Normal
- Alert

The Alert color is used only when the exact selected Value source has an active alert.

For Ping latency:

- Normal → Normal color
- High Latency → Alert color
- Offline → Alert color

An alert on another source does not recolor the displayed Value.

## Graph thresholds and colors

Non-Ping numeric graph sources may define:

- Warning threshold
- Critical threshold

Supported operators:

- `>=`
- `<=`
- `>`
- `<`
- `=`

Critical is evaluated before Warning.

Graph colors are configurable for:

- normal series
- warning
- critical
- unavailable / offline

Ping keeps its real state-driven graph colors.

## Source formatting

Monitored sources may define a display Prefix and Suffix.

Examples:

- `$`
- `°C`
- `%`
- `TH/s`

Formatting applies only to presentation. Raw values continue to drive graphing, thresholds, and alert evaluation.

## Alerts

Target Monitor provides reusable named alert definitions.

Examples:

- HighTemp
- CriticalTemp
- LowHashrate
- PoolChanged

Numeric operators:

- `>=`
- `<=`
- `=`

Text/value rules:

- `equals`
- `changed`

A monitored field may have zero, one, or multiple assigned alerts.

## Alert evaluation

Alerts are transition-based.

When a rule becomes active:

- it is recorded as active
- its configured sound plays once
- the target gains an unacknowledged alert
- a native notification may be requested when enabled

While a condition remains active, optional reminders may repeat at the configured interval.

Acknowledging an alert does not resolve it.

When the condition is no longer true, the alert resolves.

If it triggers later after resolving, it becomes a new alert event.

## Alert badge and acknowledgment

If a target has one or more unacknowledged alerts, its top-bar item shows an alert badge.

Opening the target report acknowledges currently unread alerts and clears the badge.

### Active + unacknowledged

- initial sound/notification occurs
- top-bar badge is visible
- report shows the active alert

### Active + acknowledged

- top-bar badge is cleared
- active condition remains visible
- top-bar Value remains in Alert color when that exact source is selected

### Resolved

- condition is no longer true
- alert is no longer active
- selected Value returns to Normal color

## Native notifications

Each target has independent controls for:

- Show this target in system tray
- Show alert notifications

Target Monitor emits generic `notification.show` requests through RemoteHand.

Notifications are silent at the native layer so Target Monitor's own MP3/WAV/fallback-beep audio remains authoritative.

RemoteHand queues multiple notifications for the same target tray identity.

When the current notification is clicked, hidden, or times out, the next queued notification may be displayed.

Clicking a notification restores RemoteHand and routes to:

- Target Monitor
- the originating target
- the target Report view

This navigation is carried through a generic `open-panel` action and plugin context rather than Target Monitor-specific logic in RemoteHand core.

## Reports

Each target report includes:

- overall state
- current Ping state/value
- retained Ping history
- TCP check results
- HTTP / HTTPS results
- extracted fields
- configured/active alerts

HTTP field tables support:

- search
- type/alert filtering
- pagination
- configurable page size

## Monitoring engine

The three sampler categories are independent:

- Ping
- TCP
- HTTP / HTTPS

Default intervals:

- Ping: 2 seconds
- TCP: 5 seconds
- HTTP: 10 seconds

Default retained history:

- 1 hour

Default top-bar history:

- 1 minute

The user may configure those values within the supported validation ranges.

## Appearance

Per-target appearance includes:

### Graph

- Series
- Warning
- Critical
- Unavailable / offline

### Top bar

- Target name
- Value normal
- Value alert

### Surface

- Background
- Border

Reset colors applies only to these appearance colors.

## Example: AxeOS / Bitaxe

AxeOS is a useful example of the generic HTTP / JSON model, not a hard-coded device type.

A response from `/api/system/info` may expose values such as:

- `hashRate_10m`
- `temp`
- `vrTemp`
- `power`
- `fanrpm`
- `wifiRSSI`
- `stratumURL`
- `miningPaused`
- `overheat_mode`

Example top-bar configuration:

    Title: Bitaxe
    Value: System Info · hashRate_10m
    Graph: System Info · temp

Other fields may continue to participate in background alerts.

## Architecture boundary

RemoteHand owns generic infrastructure.

Target Monitor owns monitoring semantics.

RemoteHand provides:

- executable plugin runtime
- network access/inspection
- plugin-scoped storage
- clipboard integration
- top-bar primitives
- tray contributions
- native notification transport
- panel hosting/navigation

Target Monitor provides:

- Ping behavior
- TCP monitoring
- HTTP / HTTPS monitoring
- extraction
- source formatting
- graph thresholds
- alert rules/state
- sound/reminder behavior
- target reports
- monitoring presentation

Device-specific monitoring semantics must remain outside RemoteHand core.

## Future alert delivery

v0.7.0 supports:

- sound / fallback beep
- reminders
- native Windows notifications

Future versions may add delivery sinks such as:

- email
- webhook
- file / alert log output
- other integrations

These should consume the same alert events rather than changing alert detection semantics.

## Product boundary

Target Monitor should remain generic and user-controlled.

v0.7.0 deliberately stops short of calling the product v1.0.0 so the broader alert-delivery architecture can mature without prematurely freezing that milestone.

The v0.7.0 scope is:

- proven Ping monitoring
- TCP reachability
- HTTP / HTTPS monitoring
- JSON, text, and regex extraction
- configurable sampling/history
- one top-bar item per target
- reusable alerts and reminders
- native alert notifications
- clear acknowledgment/resolution behavior
- target reports
- configurable presentation
